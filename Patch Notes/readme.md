## Suggested File Naming

Use clear release-stage filenames.

Examples:

```text
General-Release_1.0.0_patch_notes.md
Technical-Preview_0.9.5.1_patch_notes.md
Technical-Preview_0.9.4_patch_notes.md
```

---

## Release Note Structure

A good patch note should include:

1. release name/version
2. release theme
3. headline changes
4. new features
5. improvements
6. fixes
7. diagnostics/support notes
8. known limitations
9. upgrade notes if needed
10. links to related docs if useful

---

## General Release Notes

General Release notes should be written for normal users first.

They should explain:

- what changed
- why users should care
- what is safer or clearer
- what behavior changed
- what limitations remain

Avoid burying the user in implementation detail unless it affects usage.

---

## Technical Preview Notes

Technical Preview notes can be more implementation-heavy.

They may include:

- experiments
- known unstable areas
- validation notes
- candidate features
- tester warnings

If a Technical Preview candidate is later absorbed into a General Release, the General Release notes should become the authoritative user-facing summary.

---

## What Belongs Here

Good patch note content:

- feature additions
- major workflow changes
- bug fixes
- release-risk notes
- known limitations
- diagnostics additions
- user-visible behavior changes
- breaking changes
- migration/upgrade notes

Avoid:

- raw debugging transcripts
- internal scratchpad notes
- unrelated planning
- private credentials
- huge code snippets
- raw logs unless specifically necessary
